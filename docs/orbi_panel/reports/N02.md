# N02 · notification persistence

Added Drift tables for entries, delivery outbox, cursors and stable system IDs;
schema migration is additive from v13 to v14. `NotificationInboxStore.ingest`
uses one Drift transaction for entry/delivery/cursor writes and exposes read,
archive, resolve, lease reclaim and conservative cleanup operations.

Validation was run with an in-memory Drift database and the focal persistence
test. No Odoo/payment/plugin tables were changed.

Follow-up hardening: mutating operations now require scope and partition,
delivery/system-id uniqueness is installation-wide, entry upserts ignore stale
revisions, and purge is transactional while retaining pending/claimed work.
The store also exposes typed scope/partition pagination via `watch(query)` and
obtains stable system IDs from the installation registry before committing its
scope-local mirror. SharedPreferences and Drift cannot share one transaction:
a crash may leave an unused registry ID, but retrying the same semantic key
returns that ID and does not duplicate a delivery. The registry serializes
allocations in-process and its persisted mapping rejects collisions.

Evidence: notification persistence plus v10/v11/v12 migration suites pass with
18 tests total, including physical v13 reopen, offline queue preservation,
dedupe/revision, scope filtering, baseline, rollback and migration table checks.

The full core suite reached 594 tests with one unrelated existing failure in
`partner_manager_test.dart` (`credit_limit`: expected null, parsed as 0). No
notification or migration test failed; that partner contract remains a separate
red gate and is not represented here as green.

The public `NotificationSystemIdAllocator` port is injectable for N03. Core no
longer allocates `MAX(system_id)+1`; delivery requires an installation-wide
allocator, while the Drift table is only a scope-local mirror of the global ID.
