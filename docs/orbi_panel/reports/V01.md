# V01 · harness ERP2 opt-in

El harness vive en `theos_panel/lib/erp2_harness.dart` y el entrypoint en
`theos_panel/integration_test/orbi_erp2_test.dart`. Importar la librería no
hace red. La prueba normal queda omitida y sólo alcanza mutaciones cuando se
configuran simultáneamente:

- `ORBI_ERP2_ENABLE_WRITES=I_UNDERSTAND_ORBI_E2E_WRITES`.
- `ORBI_ERP2_RUN_WRITES=I_UNDERSTAND_ORBI_E2E_WRITES`.

El destino debe ser exactamente `https://erp2.tecnosmart.com.ec`; `newerp`,
puertos, rutas, query strings y logins `admin` se rechazan. El stage requiere
los cuatro actores (`SELLER`, `CASHIER`, `SUPERVISOR`, `WAREHOUSE`) con login,
ID y API key externa. No se guardan contraseñas ni claves en el repositorio,
argumentos o evidencia.

## Flujos y secuencia verificada por el harness

Cada fixture es un `sale.order` existente cuyo `client_order_ref` comienza por
`ORBI-E2E-<hex>`. El preflight lee el término de pago, el estado, el partner,
los wizards, las aprobaciones enlazadas y los modelos/campos requeridos antes
de cualquier mutación.

- Contado: vendedor/cajero ejecuta la acción comercial; si aparece una
  aprobación de crédito, supervisor la aprueba; después caja ejecuta
  `action_pos_confirm_and_invoice` con diario, método y sesión configurados.
  Se verifica factura pagada y `sale.order.payment` publicado.
- Crédito: vendedor confirma después de resolver la aprobación comercial; se
  verifica factura/despacho y se conserva la lectura de controles de crédito.
- Mixto: vendedor confirma después de la aprobación comercial; la factura
  debe existir sin picking previo. Caja aplica el wizard oficial
  `action_apply_and_create_invoice`; sólo después se acepta el picking creado
  por servidor y bodega puede asignarlo.
- FSC: vendedor resuelve la aprobación comercial, solicita FSC y supervisor
  aprueba una segunda solicitud enlazada a categoría FSC. Recién entonces
  supervisor ejecuta `action_l10n_ec_aprobar_fsc`. El pago de la factura
  existente usa únicamente el wizard nativo validado para esa venta; antes del
  pago, `button_validate` debe seguir rechazado y, después, bodega valida.

Los RPC son constantes allowlisted del contrato actual; no se aceptan nombres
de método por variables ni endpoints inventados. Los IDs usados por acciones
provienen del preflight y de las fixtures configuradas, nunca se generan en el
harness.

## Seguridad, replay y cleanup

Cada mutación vuelve a leer ERP2. Un `success: true`, HTTP 200 o respuesta
ambigua no limpia el flujo sin evidencia server-side. Los timeouts permanecen
ambiguos hasta que la lectura confirma el estado final. Aprobaciones y
pickings siempre se buscan por la venta de la fixture; no se opera sobre datos
no relacionados.

`ORBI_ERP2_CLEANUP_MODE` debe ser `retain-prefixed-fixtures`. El cleanup sólo
lee y registra las órdenes con el prefijo; no archiva, no hace `unlink`, no
escribe `active=false` y no modifica órdenes, facturas, pickings ni pagos.

La evidencia se escribe en `ORBI_ERP2_EVIDENCE_FILE` después del stage y sólo
contiene datos redactados. Esta auditoría ejecutó únicamente `flutter analyze`
y `flutter test` locales; no ejecutó ERP2 remoto.
